**既知の制約 / セキュリティ留意点**
- 署名済みPDFの NAME/TEXT/DATE はHelveticaで描画するためASCIIのみ（日本語は署名画像で担保）。
- 署名リンクは立会人型（メール到達＝本人性の根拠）。実印相当の本人確認は非スコープ。
- アップロードPDFは `path.basename` でパストラバーサルを防止済み。ただし現状は
  `uploads/econtracts` を会社横断で共有（ファイル名=ランダムUUID）。厳密なテナント境界を
  求める場合はアップロードを会社スコープで管理する改善を推奨（次段）。
- 署名リクエストの画像(dataURL)にサイズ上限を設けていない（グローバルの10MB JSON上限のみ）。
  ディスク肥大対策として将来的に署名画像の個別サイズ制限を検討。
- 認証系: 原本/署名済み/証明書PDFは `companyId` で所有チェック済み。署名系は署名者本人の
  署名欄のみ返却し情報最小化。作成/取消は ADMIN/MANAGER 限定。

## 0. エグゼクティブサマリー

契約締結業務のDX化を目的に、契約管理モジュールを「登録 → 書面作成 → 電子締結 → 保管」まで一気通貫で扱えるよう刷新する。電子サインはGMOサインの**立会人型（メール認証・事業者による証跡記録）**をベースに、**手書きサイン／印影の描画・配置**と**署名済みPDFの自動生成**を加える簡易方式とする。認証局の電子証明書やeKYCを用いる「実印相当（当事者型）」は今回の非スコープとする。

既存に電子契約の骨格（`ElectronicContract` / `EContractSignature`、署名依頼メール、`/sign/:token` 公開署名フロー）が存在するため、**ゼロからではなく既存資産の拡張**として実装する。

> ⚠️ **法務に関する注意**: 本書は電子署名法・電子帳簿保存法の解釈を断定するものではありません。「法的効力」等の表現の可否は、リリース前に必ず自社の法務・顧問弁護士のレビューを受けてください（第4章・第12章参照）。

## 1. 背景・目的

### 1.1 背景
- 警備の請負契約・業務委託契約の締結が紙・PDFメール・押印で行われ、往復に時間がかかる。
- 現行システムには電子契約の「骨格」はあるが、締結UXが「同意チェックのみ」で、GMOサインのような**書面上への署名配置**や**署名済みPDFの成果物**が無い。
- 契約登録画面（単価・現場等の管理データ入力）と電子契約フローが分離しており、締結までの導線が一体化していない。

### 1.2 目的（ビジネスゴール）
- 契約締結のリードタイム短縮（郵送・押印の往復を排除）。
- 締結済み契約書を**改ざん検知可能な形**で一元保管し、証跡（誰が・いつ・どこから署名したか）を残す。
- 「契約登録」から「締結」までを1つの導線に統合し、入力の二重化を無くす。

### 1.3 成功指標（KPI 例）
| 指標 | 現状 | 目標 |
|---|---|---|
| 契約締結リードタイム | 数日〜（郵送） | 当日〜翌営業日 |
| 締結書面のシステム保管率 | 低（メール散在） | 100% |
| 署名依頼→署名完了の追跡可否 | 不可 | 全件ステータス可視化 |

## 4. 用語と電子署名の位置づけ（重要・法務前提）

| 用語 | 本書での意味 |
|---|---|
| 立会人型（事業者署名型） | 署名者本人ではなく、サービス提供事業者（GuardSync運用者）がメール認証等で本人性を確認し、締結の証跡を記録する方式。今回のベース。 |
| 当事者型（実印相当） | 認証局が発行した電子証明書で署名者本人が署名する方式。**今回の非スコープ**。 |
| 印影 | 社印・角印などの画像。押印の代替として書面に配置する画像であり、それ自体が法的な実印を意味しない。 |
| タイムスタンプ | 第三者TSAが署名時刻を証明する仕組み（RFC3161）。今回はCould。 |

> **表記ルール（要是正）**: 現UIの「この署名は電子署名として法的効力を持ちます」「RFC3161タイムスタンプにより時刻を証明します」は、実装状況と乖離があるため、**実装に合わせた正確な表現へ改める**（例:「本サービスは立会人型の電子契約であり、署名者の同意・日時・IP等を証跡として記録します」）。最終文言は法務レビューで確定する。

## 5. 機能要件（詳細フロー）

### 5.1 全体フロー
```
[管理者]                                   [署名者(取引先など)]
  1. 契約を選択 or 新規                        
  2. 契約書PDFをアップロード                    
  3. 署名者を追加(氏名・メール)                 
  4. 署名欄を書面にドラッグ配置                 
     (署名/印影/日付/氏名 × 署名者)             
  5. 送信 → 各署名者へメール ───────────────▶ 6. メールのリンクを開く
                                              7. 書面プレビューを確認
                                              8. 手書きサイン描画 / 印影選択
                                              9. 「署名して確定」
  10. 全員完了で締結 ◀───────────────────────   (IP・UA・時刻を記録)
  11. 署名済みPDF・合意締結証明書を生成・保管    
```

### 5.2 主要ユースケース
- **UC-1 書面準備**: 管理者が契約書PDFをアップロード。システムはSHA-256を計算し保存。ページ数・サイズを取得。
- **UC-2 署名欄配置**: 管理者がPDFプレビュー上に、署名者ごとの署名欄（種別: signature / seal / date / name / text）をドラッグで配置。位置はページ番号＋正規化座標（0–1）で保存。
- **UC-3 送信**: 送信で各署名者に一意トークン付きURLをメール。ステータス `SENT`。
- **UC-4 署名**: 署名者はURLで書面と自分の署名欄を確認。署名欄をタップ→キャンバスで手書き→確定。印影欄は登録済み印影から選択。
- **UC-5 締結**: 全署名欄が埋まったら `COMPLETED`。署名画像を書面に焼き込んだ**署名済みPDF**と**合意締結証明書**を生成・保管。
- **UC-6 保管・閲覧**: 管理者は締結済みPDF・証明書・証跡をダウンロード可能。改ざん検知（保存ハッシュとの照合）。

### 5.3 バリデーション／エッジケース
- 署名リンク: 期限切れ（410）／署名済み（409）／無効（404）を明示。
- 全署名者が同一書面の別欄。1署名者が複数欄（署名＋日付＋印影）を持てる。
- 送信後の書面差し替えは不可（再送は新リビジョン扱い）。
- アップロードはPDFのみ・サイズ上限（10MB、既存踏襲）・MIME検証。

## 7. データモデル設計（Prisma 差分）

> 既存の `ElectronicContract` / `EContractSignature` を拡張し、署名欄 `SignatureField` と印影 `SealStamp`（Could）を追加。

```prisma
model ElectronicContract {
  // 既存に追加
  sourcePdfPath   String?   // アップロード原本PDF
  sourcePdfHash   String?   // 原本SHA-256（改ざん検知）
  signedPdfPath   String?   // 署名焼き込み済みPDF
  signedPdfHash   String?   // 署名済みSHA-256
  certificatePath String?   // 合意締結証明書PDF
  pageCount       Int?      // 原本ページ数
  fields          SignatureField[]
  // content は原本テキスト or メモとして残置（後方互換）
}

model SignatureField {
  id            String   @id @default(uuid())
  eContractId   String
  eContract     ElectronicContract @relation(fields: [eContractId], references: [id], onDelete: Cascade)
  signatureId   String?  // どの署名者の欄か（EContractSignature.id）
  signature     EContractSignature? @relation(fields: [signatureId], references: [id])
  type          FieldType            // SIGNATURE / SEAL / DATE / NAME / TEXT
  page          Int                  // 1始まり
  x             Float                // 正規化座標 0–1（左上基準）
  y             Float
  width         Float
  height        Float
  value         String?              // 署名画像(dataURL/パス) or テキスト
  signedAt      DateTime?
  @@index([eContractId])
  @@index([signatureId])
}

enum FieldType {
  SIGNATURE
  SEAL
  DATE
  NAME
  TEXT
}

model SealStamp {          // Could
  id         String  @id @default(uuid())
  companyId  String
  name       String
  imagePath  String
  createdAt  DateTime @default(now())
  @@index([companyId])
}
```

`EContractSignature` 側に `fields SignatureField[]` の逆リレーションを追加。ローカルは `prisma db push`、本番は `prisma migrate` 方針（現行運用に合わせる）。

## 9. 技術選定

| 用途 | 採用 | 理由 |
|---|---|---|
| 既存PDFへの署名焼き込み | **pdf-lib** | 既存PDFの読み込み・画像埋め込み・座標指定描画が可能（`pdfkit` は新規生成専用で不可） |
| 署名ページのPDF表示 | **pdfjs-dist**（PDF.js） | ブラウザで安全にPDFをレンダリングし、座標オーバーレイを重ねられる |
| 手書きサイン描画 | **signature_pad**（軽量）or 自前canvas | 依存を増やさないなら自前canvasでも可 |
| 合意締結証明書生成 | 既存 **pdfkit** | 証明書は新規生成なのでpdfkitが適する |
| ハッシュ | Node標準 `crypto`（SHA-256） | 追加依存不要 |
| タイムスタンプ（Could） | 外部TSA（例: FreeTSA）＋ `crypto` | Couldのため後続。未取得時はUI表記で担保 |

**依存追加**: `pdf-lib`, `pdfjs-dist`（フロント）, （任意）`signature_pad`。`npm audit` を実施。

## 10. セキュリティ／脅威モデル（STRIDE 抜粋）

| 脅威 | シナリオ | 対策 |
|---|---|---|
| Spoofing | 他人の署名リンクを使い署名 | トークンはUUID・一度限り・期限付き。メール到達を本人性の根拠として記録（立会人型の前提を明示） |
| Tampering | 署名後にPDFを差し替え | 原本・署名済みPDFのSHA-256を保存し、取得時に照合。署名後の原本差し替え禁止 |
| Repudiation | 署名を否認 | IP・UA・時刻・同意・ハッシュを `auditLog` と証明書に記録 |
| Information Disclosure | 署名リンクから他社契約が見える | token→署名者→契約 の紐付けのみ返す。companyId分離。最小情報のみ返却 |
| DoS | 署名エンドポイント乱打 | 既存 `rateLimit` を `/api/e-contracts/sign` にも適用。アップロードサイズ制限 |
| Elevation | 一般ユーザーが作成・送信 | `requireRole('ADMIN','MANAGER')` を全作成系に付与 |

**ファイルアップロード**: MIME＝application/pdf のみ許可、拡張子・サイズ検証、保存名はランダムUUID（既存 `docUpload` 準拠）。**保管ファイルの配信**は認証・所有チェック必須（署名者向けはtoken経由のみ）。
